# Codebase map

Where code lives, and where a change usually goes. The map lists directories, not
every file: a file's own top comment and its tests say the rest. Update this page
when a directory is added, moved or given a new job.

## Layout

```
src/
├── routes/            TanStack Router file routes; `__root.tsx` is the document shell, `_app.tsx` the
│   │                  signed-in layout; `_app/personal/` holds the staff list and each member's form
│   │                  page, `_app/dev/patrones.tsx` the style guide's pattern gallery
│   └── api/           `setup.ts` (creates an organization, behind SETUP_SECRET)
├── components/        shared pieces: `app-form.tsx` (`useAppForm` and its field components),
│   │                  `date-time-input.tsx` and `date-time-text.ts` (a date typed as `dd/mm/aaaa`, a time as `HH:mm`),
│   │                  `form-page.tsx` (a create or an edit on its own page),
│   │                  `admin-form.tsx` (the admin screens' submit step and controls), `confirm-dialog.tsx` (the question before a destructive
│   │                  action), `data-table.tsx` (every list), `app-nav.ts` and `app-sidebar.tsx` (the shell's menu),
│   │                  `page-header.tsx` (every page's title)
│   └── ui/            shadcn/ui components (see shadcn.md); add with the CLI, edit by hand
├── hooks/             every effect outside `ui/`, each in a named hook (coding-standards.md § React); shadcn's `use-mobile.ts`
├── organization/      the organization's Durable Object (ADR-0008): `organization.ts` (the class, one
│   │                  RPC method per operation) over `organization-runtime.ts` (its storage, the sign-in
│   │                  provider's accounts and `as()`, the authorization every method goes through), one module
│   │                  per area (`members.ts`, `staff.ts`, `audit.ts`, …), `accounts.ts` (the adapter over Clerk's
│   │                  Backend API), `schema.ts` (its SQLite schema) and `migrations/` (generated, applied on start)
├── dev/               the dev organization: `world.ts` (its made-up data), `seed.ts` (fills it)
├── server.ts          the Worker's entry: Start's handler, and the object class exported beside it
├── lib/               shared pure helpers: `access.ts` (roles), validation, formatting, rules;
│                      `dates.ts` (every date and time a person reads),
│                      `log.ts` (the app's one way to log, client and server)
├── server/            server-only modules that are not routes: `*.functions.ts` (server functions),
│                      `caller.ts` (the request-to-caller step: Clerk's token or the dev sign-in),
│                      `with-organization.ts` (the step in front of each server function),
│                      `organization-setup.ts` (what `api/setup.ts` runs)
├── router.tsx         the router factory; `routeTree.gen.ts` is generated and committed
├── routeTree.gen.ts   generated by the router CLI; never edited by hand
└── styles.css         Tailwind 4 and the theme tokens
scripts/               repo scripts and their unit tests (worktree port, setup, checks, the `ui` and `tests` lint plugins)
tests/e2e/             the Playwright browser suite, its seed and sign-in (see tests/e2e/README.md)
tests/lint/            the custom lint rules' tests, run through `vp lint`
docs/adr/              decisions; docs/agents/ operative rules; docs/domain/ the model
```

## Where a change goes

- **A screen**: a route file in `src/routes/`, with its loader and action beside it
  when they are small. Shared presentational pieces go in `src/components/`.
- **A query or mutation on the organization's data**: a function in the area's module
  in `src/organization/` (`members.ts`, `staff.ts`, …), taking the database
  and the acting member, and a one-line method on the `Organization` class that
  states the roles it needs and calls it.
- **A server function**: in a `*.functions.ts` file, it only calls
  `withOrganization((organization, caller) => organization.<method>(caller, data))`
  (`src/server/with-organization.ts`). A refusal comes back as `{ ok: false, reason }`.
- **A schema change**: edit `src/organization/schema.ts`, run `pnpm organization:generate`,
  and review the generated SQL. Migrations on `main` are never edited.
- **A call to an outside service**: one small adapter module the object calls and its
  tests fake, the way `src/organization/accounts.ts` wraps Clerk's Backend API.
  Nothing else imports the service's client.
- **A pure rule** (formatting, validation, state transitions): a module in `src/lib/`
  or beside its feature, tested without a database or React.

## Tests

- `*.test.ts(x)` beside the code: unit tests (`pnpm test:unit`).
- `*.workers.test.ts` beside the code: tests in the Workers runtime (`pnpm test:workers`),
  the organization object's methods on real SQLite, its fixtures in
  `src/organization/organization.test-support.ts`.
- `tests/e2e/*.spec.ts`: browser specs against the production build (`pnpm test:e2e`),
  one file per flow or race ([tests/e2e/README.md](../../tests/e2e/README.md)).
- Fixtures shared by one module's tests sit in `<name>.test-support.ts`; the object's
  tests share `src/organization/organization.test-support.ts`, and fixtures shared
  across other modules sit in a `src/test-support/` directory created when the first one is needed
  ([coding-standards.md](./coding-standards.md#test-support-files)).
